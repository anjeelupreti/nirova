# Development Log

A running record of every change to this codebase: what was done, why it was
done that way, and what alternatives were rejected. Newest entries at the
bottom.

**How to use this file.** Every change — a feature, a refactor, a deletion, a
renamed concept, a reversed decision — gets an entry. An entry that only says
*what* changed is incomplete; the value of this file is the *why*, because
that is the part that is invisible in a diff and lost within a month.

**Entry format**

```
## NNN — Title
Date · Area · Type (feature | refactor | fix | deletion | decision | doc)

**What.**   What changed, concretely.
**Why.**    The problem being solved.
**How.**    The approach, and the mechanism if it is non-obvious.
**Rejected.** What else was considered, and why it lost.
**Affects.** Files and concepts touched.
```

## 001 — Project shape: Django + DRF backend, React frontend
2026-09-02 · Whole project · decision

**What.** Backend is Django 5.1 + Django REST Framework. Frontend is a
separate React + Vite + TypeScript SPA using shadcn/ui. Two codebases, one
repository.

**Why.** The product is 130+ modules of business logic over a large
relational model — patients, stock ledgers, payroll, double-entry finance.
That is Django's home ground: the ORM, migrations, and admin remove months of
plumbing, and the transactional guarantees are what a stock ledger and a
payroll run actually need.

**How.** `backend/` (Django) and `frontend/` (React) are independent. The API
contract between them is OpenAPI, generated by drf-spectacular, so the
frontend's types can be generated rather than hand-written and drift.

**Rejected.**
- *Next.js* — was the initial choice and was reversed before any frontend
  code existed. Its server-rendering and routing strengths matter most for
  public, SEO-sensitive pages; this product is an authenticated back-office
  application where every screen is behind a login. The extra server runtime
  would be a second deployment target earning nothing.
- *Laravel* — faster CRUD scaffolding, but weaker for the real-time surfaces
  (ICU monitoring, queue displays, bed boards) and no shared type story.
- *Monolithic Django templates* — would not support the offline/degraded mode
  the spec requires for pharmacy POS and registration.

**Affects.** Repository layout, `backend/requirements.txt`, `frontend/`.

## 002 — Database per tenant
2026-09-02 · Tenancy · decision

**What.** Each customer organization gets its own PostgreSQL database. A
single *control-plane* database holds the SaaS business records.

**Why.** This system holds patient records. The strongest isolation
available, short of separate infrastructure, is a separate database: a query
that forgets its `WHERE organization_id = …` returns nothing rather than
another hospital's patients, because the rows are not there to return.

**How.** See `docs/adr/0001-database-per-tenant.md` for the full argument.
Mechanically: `apps/tenancy/` holds the tenant registry, a connection
registrar that adds databases to Django at runtime, a router that sends every
query to the right one, and middleware that binds the context per request.

**Rejected.**
- *Shared schema with `tenant_id` + row-level security* — cheapest to run and
  the industry default, but isolation rests on every query being correct
  forever, and one missing predicate is a cross-hospital data breach.
- *Schema-per-tenant (`django-tenants`)* — a reasonable middle ground, but it
  was not what was asked for, and per-database gives per-customer backup,
  restore and residency for free.

**Cost accepted.** No cross-database transactions, no cross-database foreign
keys, and migrations must fan out across every tenant. Entries 007 and 011
deal with the consequences.

**Affects.** `apps/tenancy/*`, `config/settings/base.py`.

## 003 — Two classes of app: control-plane and tenant
2026-09-02 · Architecture · decision

**What.** `CONTROL_PLANE_APPS` and `TENANT_APPS` in settings. Every app
belongs to exactly one list.

**Why.** The router needs to know, for any model, which database it lives in.
Deriving that per-model would scatter the decision; declaring it once per app
makes it reviewable in a single screen.

**How.** `TenantDatabaseRouter` reads both lists at construction and uses
them for `db_for_read`, `db_for_write` and `allow_migrate`. Because
`allow_migrate` is honoured, `migrate` against the control plane creates only
`cp_*` tables, and `migrate --database=tenant_x` creates only tenant tables.
Verified: the control-plane database has no `facility`, `role` or
`audit_event` table.

**Rejected.** A per-model `class Meta: database = …` attribute — Django has
no such hook, and a custom one would be invisible to `makemigrations`.

**Affects.** `config/settings/base.py`, `apps/tenancy/router.py`.

## 004 — A tenant model with no active tenant raises, never falls back
2026-09-02 · Tenancy · decision

**What.** `TenantDatabaseRouter` raises `TenantRoutingError` when a tenant
model is queried with no organization bound, instead of defaulting to the
control-plane database.

**Why.** A silent fallback is the worst possible failure here: a background
job that forgets to set context would write one customer's facility into the
shared database, and nothing would complain. Loud failure in development is
cheaper than silent corruption in production.

**How.** `_tenant_alias()` checks the context variable and raises with a
message that names the model and says how to fix it.

**Affects.** `apps/tenancy/router.py`, `apps/tenancy/context.py`.

## 005 — Tenant context uses `contextvars`, not thread locals
2026-09-02 · Tenancy · decision

**What.** The active organization is held in a `ContextVar`.

**Why.** Thread locals leak across `async` boundaries. Under ASGI, one thread
serves many coroutines; a thread-local tenant would let request A's
organization be visible inside request B. `ContextVar` is per-coroutine and
is inherited correctly by tasks.

**How.** `apps/tenancy/context.py` exposes `tenant_context()` as a context
manager so the previous value is always restored, including on exception.

**Affects.** `apps/tenancy/context.py`, all middleware.

## 006 — Identity lives in the control plane; clinical data does not
2026-09-02 · Identity · decision

**What.** `User`, `Membership`, `LoginAttempt` and `UserDevice` are
control-plane models. Roles and role assignments are tenant models.

**Why.** Login has to resolve *before* a tenant connection can be chosen — you
cannot look up a user in their organization's database when finding the
organization requires knowing the user. Beyond that bootstrap problem, one
person may work for two organizations in a group, and SSO/MFA are
platform-level concerns.

**How.** `RoleAssignment.user_id` is a bare `UUIDField`, not a foreign key,
because it points across a database boundary. `user_email` is denormalised
alongside it so listing assignments needs no cross-database lookup.

**Trade-off accepted.** Email addresses and names sit in a shared database.
That is a real reduction in isolation, and it is bounded: no patient,
clinical, financial or operational record leaves the tenant database.

**Rejected.** Users in tenant databases with a central email→organization
routing index — the index would hold the same emails anyway, so it buys
almost nothing while making every login two hops.

**Affects.** `apps/identity/models.py`, `apps/rbac/models.py`,
`docs/adr/0002-identity-placement.md`.

## 007 — Facility registry: a control-plane mirror of tenant facilities
2026-09-02 · Tenancy · feature

**What.** `FacilityRegistryEntry` duplicates non-clinical facility metadata
(code, name, type, status, district) into the control plane.

**Why.** Two things need facility data without a tenant connection:
1. **Quota checks.** "Does this organization already have three pharmacies?"
   must be answerable *inside the transaction* that approves a fourth.
   Opening a tenant connection mid-transaction to find out is both slow and
   impossible to make atomic.
2. **Platform analytics.** Counting hospitals across every customer would
   otherwise mean opening every tenant database in turn.

**How.** Written only by `FacilityService`, which updates both sides in one
logical operation. Holds no patient, clinical or financial data.

**Rejected.** Querying tenant databases on demand — correct but unusably slow
at the platform level, and unable to participate in the approving
transaction.

**Consequence.** Two databases cannot share a transaction, so drift is
possible. `reconcile_registry()` and the
`reconcile_facility_registry` management command detect and report it. Write
order is chosen so the surviving state after a partial failure is the safe
one: a registry row without a facility over-counts quota (visible, fixable),
whereas a facility without a registry row is invisible capacity.

**Affects.** `apps/tenancy/models.py`, `apps/organization/services.py`.

## 008 — Entitlements are layered and explain themselves
2026-09-02 · Entitlements · feature

**What.** An entitlement resolver that computes, for one organization, which
modules and features are on and what every numeric limit is — with the
provenance of each answer.

**Why.** The instruction was explicit: never gate on `plan == "premium"`.
Plans get renamed, discounted, merged and grandfathered; capabilities are
what the product actually depends on.

**How.** Four layers, weakest first:

| Layer | Source | Combines by |
|---|---|---|
| 1 | Plan | base value |
| 2 | Add-ons (× quantity) | addition |
| 3 | Grants (temporary) | addition |
| 4 | Overrides (contract) | replacement |

Overrides *replace* rather than add, because a negotiated contract term is a
statement about the final number, not an adjustment to it. Every resolved key
carries a `sources` list, so support can answer "why can this customer only
open two pharmacies?" by reading it rather than guessing.

**Rejected.** A single `limits` JSON blob on the subscription — no
provenance, no expiry, and every negotiated exception becomes a manual edit
with no record of who made it or why.

**Affects.** `apps/catalog/`, `apps/entitlements/`.

## 009 — Unknown limit keys resolve to zero, not unlimited
2026-09-02 · Entitlements · decision

**What.** `ResolvedEntitlements.limit()` returns a spec with `value = 0` for
a key nobody has defined.

**Why.** Failing closed. A typo in a limit key should stop an action, not
silently grant infinite headroom. The failure mode of "blocked, and someone
asks why" is recoverable; "unlimited, and nobody notices for a year" is not.

**Affects.** `apps/entitlements/resolver.py`.

## 010 — Per-facility-type limits derive from the overall ceiling
2026-09-02 · Entitlements · feature

**What.** A plan that says `max_facilities = 5` and nothing per type gives
every type a ceiling of 5 — but only for types whose module the customer has.
The overall ceiling still applies on top.

**Why.** Requiring every plan to enumerate all eight facility types would be
noise, and an unstated type defaulting to zero would block a perfectly
legitimate clinic. Meanwhile, a customer with 5 facilities must not be able
to open 5 clinics *and* 5 pharmacies — hence checking both.

**How.** `_derive_facility_type_limits()` fills gaps after the four layers
resolve. A type whose module is not entitled derives to 0 with the reason
recorded in `sources`.

**Affects.** `apps/entitlements/resolver.py`, `apps/catalog/keys.py`.

## 011 — Enforcement is a property of the limit, not a global rule
2026-09-02 · Entitlements · decision

**What.** Every limit carries an enforcement mode: `hard` (block), `soft`
(allow and flag), `grace` (allow until a date), `metered` (allow and bill).

**Why.** Not every ceiling should be a wall. Refusing to save a scan because
a hospital is 2 GB over its storage allowance is a decision a healthcare
system should not make on its own. Refusing a fourth pharmacy branch is
exactly right — that is a deliberate, reversible commercial act.

**How.** Storage is seeded as `metered` with an overage price; facility and
user counts are `hard`.

**Affects.** `apps/catalog/models.py`, `apps/entitlements/services.py`,
`seed_catalog`.

## 012 — Quota checks return a decision object, not a boolean
2026-09-02 · Entitlements · decision

**What.** `check_quota()` returns a `QuotaDecision` carrying the limit,
current usage, remaining headroom, enforcement mode, provenance and a list of
remediation options. It does not raise; callers opt in via
`.raise_if_blocked()`.

**Why.** A boolean can only produce a wall. Returning the full position lets
the UI say "you are using 2 of 3 pharmacies" *before* the user fills in a
form, and lets a blocked action explain itself and offer a route forward —
buy an add-on, close a facility, upgrade, or ask for an exception.

**Affects.** `apps/entitlements/services.py`,
`GET /api/org/facilities/capacity/`.

## 013 — Facility changes go through request-and-approval, not CRUD
2026-09-02 · Provisioning · feature

**What.** Opening, closing, re-opening, suspending or converting a facility
is a `FacilityChangeRequest` that is evaluated, routed to an approver, and
executed only on approval. There is no facility create/update/delete
endpoint.

**Why.** Adding or removing a hospital, clinic or pharmacy changes what the
customer pays, what their staff can do, and what the platform must support.
As a plain "New Facility" button it also becomes a way to churn capacity —
open a branch for a week, close it, open another — which makes both billing
and capacity planning fiction. Routing it through approval produces a record
of not just what the estate looks like, but why.

**How.**
1. **Evaluate** — quota decisions, module entitlement and churn history are
   computed and frozen onto the request, so a reviewer sees the position as
   it stood when the request was raised.
2. **Route** — the approval level is *derived*, never chosen by the
   requester. Inside entitlement and non-destructive → the customer governs
   it. Beyond entitlement, or churn-flagged → the platform does.
3. **Decide** — approval at the final required level executes immediately;
   there is no separate "apply" step to forget.
4. **Execute** — re-checks quota, then writes the facility and the registry
   entry.

**Rejected.** A permission (`facility.create`) and an ordinary endpoint —
enforces *who* may act but records nothing about *why*, and cannot express
"allowed, but somebody senior should look at this".

**Affects.** `apps/provisioning/`, `apps/organization/services.py`,
`apps/organization/views.py`, `apps/platform_api/views.py`.

## 014 — Approval is permission to act, not a licence to act regardless
2026-09-02 · Provisioning · decision

**What.** `execute_request()` re-runs the quota check immediately before
applying an approved change.

**Why.** Time passes between approval and execution — a scheduled request may
sit for weeks — and the customer's entitlement may have moved: a grant
expired, an add-on lapsed, another branch opened. Executing on a stale
approval would put the customer over their entitlement with an audit trail
that says it was fine.

**How.** On failure the request moves to `failed` with the blocking decisions
recorded, rather than silently proceeding.

**Affects.** `apps/provisioning/services.py`.

## 015 — Churn detection surfaces a pattern; it does not judge it
2026-09-02 · Provisioning · feature

**What.** Opening a facility of a type the organization has closed twice in
the last 90 days escalates the request to platform review.

**Why.** Closing a branch and opening another is often legitimate — a
relocation, a lease ending. It is also the obvious way to run more sites than
you pay for. Blocking it outright would punish the honest case; ignoring it
makes the limit advisory.

**How.** `detect_churn()` returns the closure history with dates and hands it
to a human, who can see a relocation for what it is. Thresholds are per
organization via `ChangeRequestPolicy`.

**Rejected.** A hard cooldown blocking re-opening for N days — punishes
relocations, and is trivially worked around by waiting.

**Affects.** `apps/provisioning/services.py`, `apps/provisioning/models.py`.

## 016 — Closing frees quota; suspending does not
2026-09-02 · Entitlements · decision

**What.** `FacilityRegistryEntry.counts_towards_quota` is True for `pending`,
`active` and `suspended`; only `closed` releases the slot.

**Why.** Suspension is a state the organization can reverse at will. If it
freed the slot, a customer could hold twice their entitlement by rotating
suspensions. Closing is a deliberate act that goes through approval and is
recorded, which is what makes it safe to honour.

**Affects.** `apps/tenancy/models.py`, `apps/entitlements/services.py`.

## 017 — Segregation of duties, declared and enforced
2026-09-02 · RBAC · feature

**What.** Permissions declare `conflicts_with` pairs
(`purchase.create` ⁄ `purchase.approve`, `payroll.process` ⁄
`payroll.approve`, `facility.request_change` ⁄ `facility.approve_change`, …).
Conflicts are reported when a role is saved, and the runtime refuses to let
one person both raise and approve the same record.

**Why.** Maker-checker is only real if it is enforced at the moment of
approval. Catching it when a role is *saved* is the earlier, cheaper warning;
catching it at approval is the one that actually holds.

**How.** `conflicting_permissions()` for the design-time check;
`_assert_may_decide()` and `assert_different_actors()` for the runtime one.
Toggleable per organization, because a two-person clinic cannot segregate
anything and would otherwise be unable to operate.

**Affects.** `apps/rbac/permissions.py`, `apps/rbac/services.py`,
`apps/provisioning/services.py`.

## 018 — Permissions are code; roles are data
2026-09-02 · RBAC · decision

**What.** The permission catalogue is a Python tuple. Roles are database rows
customers can create freely.

**Why.** A permission is a promise the application makes about what it
checks. Letting an administrator type a new permission would create one that
nothing enforces — a checkbox that does nothing, which is worse than no
checkbox. Roles carry no such promise: they are just bundles.

**How.** `Role.permissions` is a JSON list of codes, validated against
`PERMISSION_CODES` at resolution time, with unknown codes logged and ignored.

**Affects.** `apps/rbac/permissions.py`, `apps/rbac/models.py`.

## 019 — Scope filters queries; it does not just refuse them
2026-09-02 · RBAC · decision

**What.** Permissions are granted at a scope (own → own patients → unit →
department → facility → multiple facilities → organization).
`accessible_facility_ids()` turns a grant into a queryset filter.

**Why.** A department-scoped user asking for the facility list should get
*their* facility, not a 403. Refusing would be technically correct and
practically useless.

**How.** `FacilityViewSet.get_queryset()` narrows by the caller's scope.
`None` means unrestricted; an empty set means nothing is visible.

**Affects.** `apps/rbac/services.py`, `apps/common/permissions.py`,
`apps/organization/views.py`.

## 020 — Denials beat grants
2026-09-02 · RBAC · decision

**What.** A `PermissionOverride` with `is_granted = False` removes a
permission even when a role grants it.

**Why.** The entire point of withholding `refund.approve` from one manager is
that their role would otherwise carry it. A denial that could be out-voted
would be decorative.

**Note.** Organization owners bypass permission checks entirely, so a denial
against an owner has no effect. This is logged when it happens rather than
failing silently.

**Affects.** `apps/rbac/services.py`.

## 021 — The audit log lives in the tenant database
2026-09-02 · Audit · decision

**What.** `AuditEvent` and `EntityVersion` are tenant models.

**Why.** The audit log records *who read which patient's file*, which is
itself patient-identifiable. Centralising it would recreate, in one shared
table, exactly the exposure that database-per-tenant exists to prevent.

**How.** Append-only by database grant (INSERT + SELECT for the application
role), not by an ORM guard — a guard in application code is theatre, since
anything that can bypass the ORM bypasses the guard.

**Affects.** `apps/audit/`, `docs/security/audit-immutability.md`.

## 022 — Audit writes never raise
2026-09-02 · Audit · decision

**What.** `record()` catches every exception and logs it.

**Why.** A nurse recording vitals must not be blocked because the audit
table is unavailable. The clinical action is the thing that matters; a
missing log line is a platform incident, not a patient-facing failure.

**How.** Failures are logged at `exception` level with the action and actor,
so they are loud in monitoring even though they are silent to the user.

**Affects.** `apps/audit/services.py`.

## 023 — Audit diffs store changed fields only
2026-09-02 · Audit · decision

**What.** `diff_instance()` records only fields that changed, with a redaction
list for secrets.

**Why.** Storing full before/after copies would duplicate the medical record
into the audit log — multiplying the data at risk for no investigative gain.
Records where full history genuinely matters (prescriptions, invoices,
clinical notes, compensation) use `EntityVersion` snapshots instead.

**Affects.** `apps/audit/services.py`.

## 024 — One error envelope for the whole API
2026-09-02 · API · decision

**What.** Every error returns `{"error": {"code", "message", "detail"}}`.

**Why.** The frontend renders one error component and branches on `code`
rather than parsing prose. It also means a new error type cannot accidentally
ship in a shape nothing handles.

**How.** `api_exception_handler` rewraps DRF, Django validation, 404 and
permission errors into the same shape. `DomainError` subclasses carry their
own code and status.

**Affects.** `apps/common/exceptions.py`, `config/settings/base.py`.

## 026 — Three dataclass fields were silently not fields
2026-09-02 · Entitlements, Audit · fix

**What.** `ResolvedEntitlements.resolved_at`, `LimitSpec.overage_unit_price`
and four `AuditContext` attributes were written as `name = None` without a
type annotation, making them class attributes rather than dataclass fields.
Annotated as `object = None`.

**Why.** Found at runtime: `ResolvedEntitlements(resolved_at=…)` raised
`TypeError: unexpected keyword argument`. `AuditContext` would have failed
the same way on the first authenticated request — the audit middleware passes
all four by keyword.

**Lesson.** `@dataclass` silently ignores un-annotated assignments. Worth a
lint rule.

**Affects.** `apps/entitlements/resolver.py`, `apps/audit/services.py`.

## 030 — Tenant middleware authenticates the JWT itself
2026-09-02 · Tenancy · fix

**What.** `TenantContextMiddleware` now calls
`JWTAuthentication().authenticate(request)` when `request.user` is anonymous,
and publishes the result onto the request.

**Why.** Found by smoke-testing the API: `/api/auth/session/` returned
`organization: null` and `/api/org/facilities/capacity/` returned 403 for a
user who demonstrably had both. The cause is an ordering problem that is easy
to miss and total in effect:

- Django's `AuthenticationMiddleware` populates `request.user` from the
  **session**. This is a token-authenticated API, so it always yielded
  `AnonymousUser`.
- DRF authenticates the bearer token **inside the view**, via
  `APIView.initial()`.
- The tenant middleware runs between those two, so it never saw an
  authenticated user and never bound an organization.
- The database router therefore had no tenant for every single request.

Nothing in the stack complained; the system simply behaved as though every
caller were logged out.

**How.** The middleware verifies the token itself. The cost is one extra
signature verification per request — DRF still authenticates independently in
the view. That is cheap, and the alternative designs are worse:

- *Resolve the tenant lazily on first use* — the router needs the context
  variable set, and a lazy value cannot set a `ContextVar` retroactively for
  code already running.
- *Bind the tenant in a DRF base view* — works, but only for views that
  remember to inherit it. Middleware cannot be forgotten.

A bad token is deliberately **not** rejected in middleware: that is DRF's
job, and doing it here would bypass the API error envelope and return a bare
Django 401. The request proceeds with no tenant, and the view's own
authentication produces the correct, well-formed error.

**Affects.** `apps/tenancy/middleware.py`.

## 032 — Frontend scaffold: React + Vite + TypeScript
2026-09-02 · Frontend · feature

**What.** `frontend/` scaffolded with Vite's `react-ts` template, plus
Tailwind and shadcn/ui component primitives.

**Why.** shadcn/ui is copy-in source rather than an installed dependency, so
components can be edited directly — which matters for a product that will
need dense, domain-specific tables and forms that no generic component
library gets right (batch selection with expiry dates, bed boards, triage
queues).

**How.** The API client attaches the bearer token and the `X-Organization`
header on every request. The organization header is what makes the context
switcher work: the same screens re-render against a different tenant purely
by changing that value.

**Affects.** `frontend/`.

## 033 — Facility-type limit add-ons were unsellable without module add-ons
2026-09-02 · Catalogue · fix

**What.** Added `module_hospital`, `module_clinic`, `module_pharmacy`,
`module_laboratory` and `module_warehouse` add-ons.

**Why.** Found while approving a real request. `check_facility_quota` asks
three questions, and the first is "is the module entitled at all?" (entry 013).
The seeded catalogue had `extra_hospital`, which raises the *count* — but no
way to buy the hospital *module*. So a platform approver faced with a customer
who wanted a hospital had nothing to sell them: the capacity existed in the
catalogue but was unreachable.

**Lesson.** A per-type limit add-on is meaningless without the module add-on
for that type. Any new facility-bearing module needs both, or its capacity
cannot be sold.

**Affects.** `seed_catalog`.

## 034 — An approver can attach several add-ons in one decision
2026-09-02 · Provisioning · feature

**What.** `decide()` and the decision endpoints accept `granted_addons`, a
list of `{code, quantity}`. The single-add-on arguments remain for the common
case.

**Why.** Directly out of entry 033: making a hospital request fit needs *two*
purchases — the module and the slot. Forcing two separate decisions would put
the request into an incoherent state between them, where the module is bought
but the count still says zero.

**How.** `_normalise_addon_grants()` collapses both argument forms into one
list and sums duplicate codes, so a caller passing the same add-on twice does
not silently double the customer's bill.

**Affects.** `apps/provisioning/services.py`,
`apps/organization/serializers.py`, `apps/platform_api/views.py`.

## 035 — Soft delete and unique constraints were fighting each other
2026-09-02 · Data model · fix

**What.** Every unique constraint on a soft-deletable model is now partial:
`condition=Q(deleted_at__isnull=True)`.

**Why.** Found by re-running `seed_catalog`, which failed with
`duplicate key value violates unique constraint "uniq_module_per_plan"`.

The cause is general, not a seed problem. `SoftDeleteQuerySet.delete()` sets
`deleted_at` rather than removing the row — so the row is still in the table,
still occupying the unique key, still blocking anything that wants to reuse
that value. Every soft-deletable model with a unique constraint had this:

- a customer closing facility `MKC-KTM` could never reuse that code;
- a revoked membership blocked re-inviting the same person;
- re-seeding a plan's modules was impossible.

Each would have surfaced as an integrity error saying nothing useful about
what actually went wrong.

**How.** Partial constraints on `PlanModule`, `PlanFeature`, `PlanLimit`,
`FacilityRegistryEntry`, `Department`, `Unit`, `ConfigSetting`, `Membership`
and `UserDevice`. Uniqueness now holds among *live* rows, which is what was
meant all along.

**Also.** The seed uses `hard_delete()` for plan join rows. Those are
structural — a plan's module list is a definition, not an event — so
tombstoning them serves nobody.

**Lesson.** Adding `SoftDeleteModel` to a model with a unique constraint is
never a drop-in change. Worth a check in review.

**Affects.** `apps/catalog/models.py`, `apps/tenancy/models.py`,
`apps/organization/models.py`, `apps/identity/models.py`, `seed_catalog`,
four migrations.

## 036 — A failed execution rolls back its own approval
2026-09-02 · Provisioning · doc

**What.** Documenting behaviour discovered by testing, not a change.

Approving a request whose capacity no longer fits raises inside
`execute_request()`. Because `decide()` is `@transaction.atomic`, that
exception rolls back *the whole decision* — the `ChangeRequestDecision` row,
the status change, everything. The request is left exactly as it was, open and
awaiting a decision.

**Why this is right.** An approval that authorised something impossible was
never a valid approval. Recording it would leave a request marked "approved"
that had not happened, and a decision log claiming someone signed off on
something that could not be done. Rolling back leaves the approver able to
retry with the capacity attached — which is the actual fix.

**Note for future refactoring.** This behaviour depends on `execute_request()`
being called *inside* `decide()`'s transaction. Moving execution to a
background task or a `transaction.on_commit` hook would break it: the approval
would then commit and the execution would fail separately, producing exactly
the incoherent state described above. If execution is ever made asynchronous,
the request must move to an explicit `failed` state that can be retried.

**Verified.** Approving `FCR-2026-0004` without capacity was refused; the
request stayed at `platform_review` with only the earlier organization
approval recorded. Approving again with the module and the slot executed
cleanly.

**Affects.** No code. `apps/provisioning/services.py` behaviour.

## 037 — Decision responses re-fetch before serializing
2026-09-02 · API · fix

**What.** Both `decide` endpoints re-query the request before serializing the
response.

**Why.** The object came from a queryset with `prefetch_related("decisions")`,
and that cache was populated *before* the new decision existed. The response
therefore omitted the very decision the caller had just made — a UI rendering
it would show the approval as not having happened.

Small bug, and a misleading one: it looks exactly like the write failing.

**Affects.** `apps/platform_api/views.py`, `apps/organization/views.py`.
